# HIS 상병코드(진단) 동봉 요청서 — billing.line_recorded payload 확장

> **목적**: 사전심사의 **의학적 타당성** 판단(예: 산정횟수 초과가 다발성 상병으로 정당한가)과
> **케이스 종합 AI 검토** 컨텍스트를 위해, 진료라인 수신 시 **상병코드(진단)**를 동봉 요청.
> 현재 ERP는 행위·약제·자격·단가만 받아 형식·산정 심사만 가능 — 상병이 의학적 심사의 변곡점.
>
> **작성**: 2026-06-14 (ERP) | **대상**: HIS 청구/연동 담당 | **선행**: `his-billing-lines.request.md`(기존 계약)
> **상태**: 📨 HIS 회신 대기 — **ERP 수신·표시·AI 측 구현 완료**(아래 §3), HIS 송신만 시작하면 즉시 활용

## 1. 요청 — 한 필드 추가

기존 `billing.line_recorded` payload에 **`diagnosisCodes` 하나만** 추가해 주세요. (나머지 계약 동일)

```jsonc
{
  "event": "billing.line_recorded", "source": "his",
  "ref": "bline:{encounterId}:{lineId}", "occurredAt": "...",
  "payload": {
    "chartNo": "C-2026-0001",
    "encounterId": "enc-uuid",
    "code": "AA157", "codeType": "TARIFF", "count": 1,
    "treatedOn": "2026-06-15",
    // ... 기존 필드 동일 ...
    "diagnosisCodes": ["S52.50", "M84.30"]    // ★추가 — 해당 에피소드 상병(주상병 먼저, 부상병 순)
  }
}
```

### 필드 규격
| 항목 | 값 |
|------|-----|
| **키** | `diagnosisCodes` |
| **형식** | **배열**(권장) `["S52.50","M84.30"]` 또는 **쉼표문자열** `"S52.50,M84.30"` — ERP 양쪽 수용 |
| **코드체계** | **KCD/ICD 상병코드**(청구명세서 상병). 소수점 포함 가능 |
| **순서** | **주상병 먼저**, 부상병 순(의학적 판단 시 주상병이 핵심) |
| **단위** | **에피소드(encounter) 단위** 상병 — 같은 encounterId 라인들엔 **동일 목록 반복 전송**해도 됨(ERP가 케이스 단위로 중복 제거) |
| **길이** | 합산 ≤120자(초과 시 ERP가 절단 저장 — 주상병 우선이라 안전) |
| **선택** | 없으면 생략/`null` — ERP는 "미수신" 안내로 표시(에러 아님) |

> EDI 청구명세서엔 원래 상병이 포함되므로, HIS가 명세서 작성 시점의 상병을 그대로 동봉하면 됩니다.

## 2. 활용 (ERP 측)
1. **명세 헤더에 상병 표시** — 심사자가 진단 맥락을 보며 판단.
2. **AI 종합검토 컨텍스트** — 적발별 AI 진단 시 상병을 투입해 의학적 타당성 보조(예: "S52.5 다발성 골절 → 고정술 3회 정당" 근거 탐색). 비식별 게이트·판단보류·휴먼인더루프 유지.
3. **(후속) 상병-조건 룰** — 적응증·상병별 산정상한 등 상병 기반 자동 판정 확장 여지.

## 3. ERP 측 준비 완료 (2026-06-14, PR #206)
- `billing_lines.diagnosis_codes` 컬럼(마이그 0058) — `diagnosisCodes` 수신 저장(list/문자열 수용).
- `case_diagnoses` 집계 → 진료비 명세 헤더 상병 표시.
- `POST /pre-review/cases/{id}/ai-review` — 상병 컨텍스트 투입 AI 종합검토.
- **HIS 송신 시작만 하면 코드 변경 없이 즉시 흐름**(현재 미수신이라 "HIS 미수신" 표시 중).

## 4. 비식별·보안
- 상병코드는 **비식별 코드**(개인식별정보 아님) — 자유서술 진단명/진료기록은 보내지 마세요(PII 게이트가 차단).
- AI 전송 전 ERP가 비식별 검증(filter_gate) 후 코드만 전달.

## 5. (추가 요청) 시술 부위/측 — `procedureSite` (의학적 타당성 핵심)

> **배경**: 산정횟수 초과 적발(예: N0983011 체외금속고정술 **3회** > 상한 1)이 **의학적으로 정당한가**는
> **시술 부위·측(좌/우, 동측/양측)** 에 좌우됩니다. 부위가 다르면 다회 산정이 정당 — 상병만으로는
> 부족하고, **부위 정보가 있어야 사전심사가 직접 판단**(없으면 의료진 질의로 우회).

기존 `billing.line_recorded` payload에 라인별로 **`procedureSite` 하나** 추가 요청(선택 필드).
```jsonc
"payload": {
  "code": "N0983011", "count": 3, "treatedOn": "2026-06-11",
  // ... 기존 + diagnosisCodes ...
  "procedureSite": "LT_RADIUS"     // ★추가 — 시술 부위/측(코드 또는 약어). 없으면 생략
}
```
| 항목 | 값 |
|------|-----|
| **키** | `procedureSite` |
| **형식** | 짧은 코드/약어 문자열(≤20자). 예: `LT`(좌)·`RT`(우)·`BIL`(양측)·`LT_RADIUS`·부위코드 |
| **단위** | **라인(행위) 단위** — 같은 코드라도 부위가 다르면 라인별로 다른 값 |
| **체계** | HIS 표준 부위코드 우선, 없으면 약어. ERP는 문자열 그대로 보관·표시(비식별) |
| **선택** | 없으면 생략/`null` — ERP는 "부위 미수신" 표시(에러 아님) |

> **비식별**: 부위 코드/약어는 개인식별정보 아님. 자유서술 수술기록은 보내지 마세요(PII 게이트 차단).
> **ERP 준비**: 수신 시 명세 라인에 부위 표시 + 산정횟수 룰의 "부위 상이" 정당성 판단 보조(후속). 송신만 시작하면 활용.
