## 1. Overview

### 1.1 Purpose

중소~중형 병원(단일 기관)의 운영 전반 — 인사, 재무, 재고, 원무, **건강보험 심사 대응, 규제 준수, 원가 관리** — 을
하나의 통합 시스템으로 관리하여, 수기/엑셀 행정 업무를 디지털화하고 **심평원 삭감 리스크와 고시·의료법 변동에
체계적으로 대응**한다.

### 1.2 Background

- 일반 기업형 ERP와 달리 국내 의료기관은 **건강보험심사평가원(심평원) 심사 체계, 보건복지부 고시(수가/약제/치료재료), 의료법·전공의법 등 특수 규제**가 업무의 중심
- **병원은 현재 HIS(EMR/OCS)와 그룹웨어를 운영 중** — 본 ERP는 행정·심사·규제 영역을 담당하고 HIS·그룹웨어·심평원·공공 API와 연계
- 시스템 프로파일: **트래픽 저부하(동시 ~50명) × 도메인 고복잡(심사·고시·규제)의 비대칭 시스템** → 분산 아키텍처가 아닌 도메인 경계·데이터 정합성 중심의 Enterprise 설계
- v0.2(Dynamic BaaS MVP)에서 의료기관 특화 PRD 전체 채택과 함께 **Enterprise 레벨로 전면 재기획** (2026-06-07 결정)

## 2. Scope

### 2.1 모듈 구성 (8개 Bounded Context — Costing은 2차 활성화)

> "단계" 컬럼은 모듈의 최초 활성화 Phase. 개별 기능의 Phase는 §3.1 FR 테이블의 Phase 컬럼이 기준 (예: Claims 모듈은 1차 활성화지만 사전심사 룰엔진 FR-41은 2차).

| # | 모듈 | 책임 | 단계 |
|---|------|------|:---:|
| 1 | **공통 기반** | 인증/RBAC(면허 권한 플래그)/조직/알림/감사 | 1차 |
| 2 | **HR** (Healthcare HR) | 직원·면허·근태·듀티·급여기초·간호등급 입력원·전공의법 검증 | 1차 |
| 3 | **Finance** (재무/회계) | 전표·예산·정산·삭감 손실 전표 (집계 종착) | 1차 |
| 4 | **SCM** (물류/재고) | 품목·로트·유효기간·FIFO·마약류 수불부·UDI(2차) | 1차 |
| 5 | **Patient** (원무) | 환자기본(최소화)·접수·수납·예약·HIS 수신 | 1차 |
| 6 | **Claims** (의료보험) ★신규 | 심사결과통보서 매핑·삭감 분류·이의신청·사전심사 룰엔진(2차) | 1차 |
| 7 | **Regulatory** (규제대응) ★신규 | **수가/약제/재료 마스터 버전관리(temporal)**·고시 동기화·간호등급 산식·노동규제 룰 — **마스터 단일 소스** | 1차 |
| 8 | **Costing** (원가) ★신규 | ABC 원가·삭감 귀속 (읽기 전용 집계) | 2차 |

### 2.2 In Scope — Phase 1 (1차 릴리스)

**공통 기반**
- [ ] 인증(JWT)·RBAC 4단계 + **면허 미갱신 시 권한 제한 플래그** (PRD 4.2)
- [ ] 부서/직급 조직 관리, In-app 알림 센터, 역할별 대시보드, Excel 내보내기, 감사 로그

**Regulatory (시스템의 심장 — 최우선)**
- [ ] 수가/약제/치료재료 마스터 공공 API 자동 동기화 (PRD 3.1)
- [ ] **수가 마스터 버전관리** — 고시 적용일자별 이력(valid_from/to), 과거 시점 단가 정확 재현 (PRD 3.2)
- [ ] 간호등급제 산식·노동규제(근로기준법·전공의법) 룰 보관
- [ ] **공시(고시·규정) 원문 관리** — 불변 ID + revision 버전, 시행일/폐지 상태, 분류 코드, 본문 텍스트(UTF-8) + 첨부 분리
- [ ] **AI 검색 서비스(example.org) 색인 발신 연계** — 등록/개정/폐지 이벤트 REST 발신, content_hash 정합성 (상세: `references/weve-ai-integration-reply.md`)

**HR**
- [ ] 직원·발령 이력, 자격·면허 관리(만료 알림 + 권한 플래그 연동)
- [ ] 근태 — 그룹웨어 출퇴근 연계 수신, 집계·조회
- [ ] 연차 자동 부여 + 신청·승인 워크플로우
- [ ] 교대근무(듀티) 수동 편성 (D/E/N/OFF) + **근로기준법(주52h)·전공의법(주80h) 위반 경고** (PRD 3.4)
- [ ] **간호등급제 모니터링** — 듀티 데이터 × 재원 환자 수 기반 가산/감산 일일 모니터링 (PRD 3.3)
- [ ] 급여 기초 데이터(수동 입력)·명세 조회·PDF, 재직·경력증명서 발급

**Claims (의료보험)**
- [ ] **심평원 심사결과통보서 자동 파싱·매핑** (청구포털/HIS 청구 모듈 경유 수신) — 삭감/반송 내역을 환자별·진료과별·의사별·약제/재료별 자동 분류 (PRD 1.2)
- [ ] **이의신청 워크플로우** — 접수→보완→기각/인정 트래킹, 확정 삭감액 손실 전표 자동 처리 (PRD 1.4)
- [ ] 진료과별/의사별 삭감 통계 대시보드 (PRD 1.3 일부 — 통계만, ABC 귀속은 2차)

**SCM**
- [ ] 품목 마스터 (로트·유효기간 필수 입력)
- [ ] **FIFO 기반 재고 차감 + 유효기간 임박(3개월) 알림·출고 제한** (PRD 2.1)
- [ ] 안전재고 미달 알림
- [ ] 마약류 수불부 별도 관리 + 수불일지 출력 (법적 의무)
- [ ] 발주 요청→승인→입고 워크플로우

**Patient (원무)**
- [ ] 환자 기본정보 (이름·생년월일·차트번호·연락처로 최소화, 주민번호 미저장)
- [ ] 외래 접수·수납, 예약 캘린더, 일별 수납 마감 → 재무 전표 자동 생성
- [ ] HIS 연계 수신 (환자 기본정보·수납 데이터)

**Finance**
- [ ] 수입/지출 전표, 계정과목, 부서별 예산·집행률, 월별 정산 리포트
- [ ] 보험 청구 현황 (Claims 모듈과 연계), 삭감 손실 전표 수용

**외부 연계 (Integration Layer)**
- [ ] HIS → ERP: 환자·수납 데이터 (HL7/FHIR/API/파일 — Phase 0 확정)
- [ ] 그룹웨어 → ERP: 출퇴근 기록
- [ ] 심평원 심사결과통보서 수신 → Claims (청구포털/HIS 청구 모듈 경유)
- [ ] 공공 수가 API → Regulatory
- [ ] **ERP → AI 서비스(example.org): 공시 색인 발신** — **연동 스펙 v1.0 확정** (폴링 단독 모드 공식화, callback 제거. ERP·AI 양측 회신: `references/weve-ai-integration-reply.md`, `references/notice-integration-reply-from-ai.md`)
- [ ] 공통 원칙: Anti-Corruption Layer, 스테이징 테이블 경유, 실패 행 격리·재처리

### 2.3 Phase 2 (2차 — 자동화·추적성 심화)

- 사전심사 룰엔진 — 처방·재료 소모 입력 시 심평원 고시 기준 실시간 스크리닝 (PRD 1.1)
- 삭감 손실 ABC 원가 귀속 (PRD 1.3) + 진료과별/행위별 ABC 원가 계산 (PRD 5.1) — Costing 모듈 본격화
- UDI 역추적 — 리콜 시 사용 환자 역추적 (EMR 양방향 필요) (PRD 2.2)
- 수술실/처치실 바코드·RFID 실시간 차감·빌링 연동 (PRD 2.3)
- 자동 듀티 생성 — 직군별 유연 근무 템플릿 (PRD 4.1)

### 2.4 Out of Scope

- EMR/OCS 자체 기능 (진료기록 작성·처방 입력은 HIS 영역)
- 심평원 **청구서 발송**(EDI 송신) — 수신·분석만 (송신은 HIS/청구 프로그램 영역)
- 급여 자동 계산 엔진 (4대보험·소득세 자동화) — 공제액 수동 입력
- 자체 출퇴근 기록 기능 — 그룹웨어 활용
- **ERP → HIS** 역방향 데이터 전송에 한정한 제외 (단, Phase 2 바코드 빌링·UDI는 예외로 별도 설계). ※ ERP → AI 서비스(example.org) 발신은 HIS와 무관한 별도 아웃바운드 연계로 In Scope(§2.2)임
- SMS/카카오 알림톡, 모바일 네이티브 앱, 다기관(멀티 테넌트)

### 4.2 Quality Criteria

- [ ] Lint 에러 0건, 빌드 성공
- [ ] 권한 우회 불가 검증 (§3.3 매트릭스 기준)

## 5. Risks and Mitigation

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| **HIS 서버 동거에 따른 리소스 경합** (ERP를 HIS 구동 서버에 설치 — HIS는 진료 핵심 시스템) | High | Medium | 컨테이너 CPU/메모리 상한 설정 필수, 배치 작업은 HIS 피크 시간(진료시간) 회피, 가용 리소스 사전 확인 (M0b) |
| **HIS 동거에 따른 측면 이동(lateral movement)** — ERP 침해 시 HIS(진료 데이터)로 전이 가능 | High | Medium | DB 계정·스키마 분리(NFR), 컨테이너 격리, ERP↔HIS 통신을 ACL 인터페이스로 한정. DB 공유 형태·계정 분리 가능 여부 Phase 0 확정 (M0b) |
| **AI 발신 경로를 통한 민감정보 유출** — 공시 본문에 환자/직원 정보 혼입 가능 (격리망의 유일한 정규 아웃바운드) | High | Medium | FR-53 필터링 게이트 + 분류 화이트리스트, 발신 감사 기록. 개인정보 위탁 해당 여부 법적 검토 (M0f) |
| 기존 DB 서비스 종류·버전 미확인 (PostgreSQL 여부) | Medium | Medium | 구현 착수 전 DB 정보 수령 (사용자 전달 예정). PostgreSQL이 아닐 경우 temporal 설계·ORM 방언 조정 |
| 프록시 화이트리스트 등록 지연 (공공 수가 API·심평원 도메인) | Medium | Medium | Phase 0에서 등록 대상 도메인 목록 확정 후 정보보안팀 신청 (M0b) |
| **HIS 연계 방식 미확정** (HL7 v2/FHIR/API/파일) | High | High | Phase 0 벤더 확인 (M0a). 동일 서버 동거로 파일/로컬 소켓 연계도 옵션. ACL 인터페이스 선고정·구현체 후행 |
| **심평원 통보서 수신 채널 변경됨** — 기존 KT EDI는 2025.3 종료, **청구포털로 일원화**. 통보서는 청구SW(HIS 청구 모듈)가 수신할 가능성 높음 | High | Medium | 수신 경로를 ① HIS 청구 모듈 파일/DB 연계(유력, 동거 서버) ② 포털 다운로드→업로드(fallback)로 설계. 실물 샘플 확보 전 매핑 구현 착수 금지 (M0c). 상세: `docs/01-plan/references/hira-review-notice-reference.md` |
| **수가 버전관리 설계 오류** (시점 단가 부정확 → 정산 오류) | High | Medium | temporal 모델(valid_from/to) 정밀 설계, 과거 정산 재현 E2E 필수 |
| 범위 과대 (7개 모듈 + 4종 연계) | High | High | Phase 1/2 경계 고정, Costing·룰엔진·UDI·바코드는 2차 격리. 모듈별 PDCA 분리 |
| 자체 백엔드 보안 결함 — 인증·행 수준 권한 필터 직접 구현에 따른 취약점 노출 | Medium | High | RBAC+행 필터를 서비스 레이어에 내재화, 보안 리뷰(security-architect) 통과 후 운영 |
| 의료 도메인 검증 능력 (심사 기준·고시 해석) | High | Medium | 의료보험팀·약제팀 도메인 전문가 상시 리뷰 루프. AI 생성 룰 무검증 채택 금지 |

## 6. Architecture Considerations

### 6.1 Project Level Selection

| Level | Characteristics | Selected |
|-------|-----------------|:--------:|
| Starter | Simple structure | ☐ |
| Dynamic | Feature-based modules, BaaS | ☐ (v0.3에서 폐기) |
| **Enterprise** | **Modular Monolith + Async Workers, Clean Architecture, 자체 백엔드** | ☑ |

> **결정**: "Enterprise = 마이크로서비스"가 아님. 동시 ~50명 저부하 × 고복잡 도메인이므로
> 분산 시스템 대신 **엄격한 모듈 경계 + 데이터 정합성 + 규제 대응 깊이**에 투자.
> 풀 MSA는 분산 트랜잭션·운영 부담으로 명시적 기각.

### 6.2 Key Architectural Decisions

| Decision | Selected | Rationale |
|----------|----------|-----------|
| 아키텍처 스타일 | **하이브리드: Modular Monolith 코어 + 비동기 워커 2종** (Integration / Batch) | 수납→전표→원가는 단일 DB 트랜잭션. EDI 파싱·마스터 동기화·간호등급 배치는 워커로 격리 |
| 백엔드 | **Python + FastAPI** (자체 백엔드 — v0.3 결정) | 룰엔진·통보서 파싱·temporal 쿼리·복잡 트랜잭션의 직접 제어 필요. Python 생태계가 데이터 매핑·배치에 우위 |
| ORM/마이그레이션 | SQLAlchemy 2.x (async) + Alembic | temporal 테이블·복잡 조인 제어 |
| DB | **기존 DB 서비스 활용** (서버에 운영 중 — 종류·버전 구현 시 확인. PostgreSQL 기준 설계, 상이 시 조정) + 논리 스키마(모듈별) | 트랜잭션 정합성·temporal 쿼리·감사. 규모상 샤딩 불필요. DB 컨테이너 번들 불필요 |
| 캐시/큐 | **Redis (캐시 + Streams 워커 큐 겸용)** | 50명 규모에 RabbitMQ 과잉. 부족 시 승격 |
| 룰엔진 | 1차: 코드형 룰(정책 클래스) → 2차: 데이터 주도 룰테이블 + 평가기 | 1차 룰 수 제한적(간호등급·전공의법·FIFO). 별도 룰엔진 제품 도입은 과잉 |
| 프론트엔드 | Next.js + TypeScript + TanStack Query + Tailwind/shadcn | v0.2 선택 유지 (전환 비용 0) |
| 인증 | 자체 JWT + RBAC + 면허 권한 플래그 | BaaS Auth 의존 제거, PRD 4.2 내장 |
| 외부 연계 | **Anti-Corruption Layer + 스테이징 테이블** 패턴 | HIS 방식 미확정이므로 어댑터 인터페이스 선고정, 구현체 교체 가능 |
| 배포 | **Docker Compose — HIS 구동 서버 내 설치 (확정)**. 컨테이너 CPU/메모리 상한 필수, 배치는 진료시간 외 스케줄 | 기존 격리 서버에 Linux+Docker 가용. HIS 영향 최소화가 최우선 제약 |
| 인프라 위치 | **격리 on-prem 서버 (확정)** — 외부 통신은 프록시/화이트리스트 경유 | 수가 API·심평원 도메인 화이트리스트 등록 필요. 아웃바운드 호출은 모두 프록시 설정 경유 |
| 백업/DR | pg_dump 일배치 + WAL 아카이브 + 오프사이트 사본 — **암호화 저장·키 분리 보관·매체 접근 통제** (NFR 백업 보안) | 의료기록 보존연한 대응, 평문 백업 반출은 운영 통제 우회 경로가 되므로 금지 |

### 6.3 Monorepo Structure

```
hospital-erp/
├── apps/
│   └── web/                  # Next.js 프론트엔드
├── services/
│   ├── core/                 # FastAPI 모듈러 모놀리스
│   │   └── src/
│   │       ├── common/       #   인증/RBAC/알림/감사
│   │       ├── hr/           #   인사 (듀티·간호등급 입력·노동규제 검증)
│   │       ├── finance/      #   재무 (전표 인터페이스 단일화)
│   │       ├── scm/          #   재고 (FIFO·마약류)
│   │       ├── patient/      #   원무
│   │       ├── claims/       #   의료보험 (통보서 매핑·이의신청)
│   │       ├── regulatory/   #   규제 마스터 (temporal 버전관리) ★단일 소스
│   │       └── costing/      #   원가 (2차)
│   ├── worker-integration/   # HIS·그룹웨어·통보서 수신 + AI 발신 어댑터 (ACL)
│   └── worker-batch/         # 통보서 파싱, 수가 동기화, 간호등급 일배치
├── packages/
│   └── shared-types/         # API 스키마·통보서/마스터 타입 단일 소스
├── infra/                    # docker-compose, 환경 설정
└── docs/                     # PDCA 문서
```

**모듈 경계 원칙**
1. Regulatory가 단가·인정기준의 **단일 소스** — 타 모듈은 복제 금지, 적용일자 기준 조회만
2. 전표 생성은 Finance 인터페이스로만 (Patient/Claims/SCM이 직접 쓰기 금지)
3. Costing은 읽기 전용 집계 — 타 모듈 트랜잭션 불개입
4. 모듈 간 직접 테이블 조인 금지 — 서비스 레이어 인터페이스 호출만
