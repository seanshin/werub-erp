# 심평원 EDI 청구 생성 — 스코핑 & 단계 계획 (D3 완성)

> HIS 원무·심평원 요청: EDI 청구파일 포맷·수가 산정·비급여·묶음(bundling) 규칙 — 청구 파운데이션(D3)
> 스텁을 **실 청구 생성**으로 완성 + 실 EDI 수가코드표(현 dev seed B0010 대체).
>
> ⚠ **대형 도메인 프로젝트** — 무작정 구현 시 잘못된 EDI 포맷으로 심평원 반려. 실 스펙·데이터·시험청구가
> 선행돼야 하는 부분과 지금 착수 가능한 부분을 구분한다.

## 현재 상태 (이미 있는 것)

| 자산 | 상태 |
|---|---|
| `regulatory.FeeMaster` | 수가/약제/치료재료/비급여 **temporal 마스터**(code_type TARIFF/DRUG/MATERIAL/NONCOVERED·unit_price·benefit_type 급여/비급여·기간겹침 EXCLUDE·성별/연령 제한). **현 dev seed(B0010 등 대표값)** |
| `job_fee_sync`/`fee_sync.py` | data.go.kr(apis.data.go.kr/B551182) **실 수가 동기화 어댑터 완성**·SSRF 화이트리스트·**serviceKey 미설정 시 대기 모드** |
| 의약품 표준코드 | 심평원 305,522건 **prod 적재 완료**(drug_std) |
| `claims/edifact.py` | EDIFACT **파서(인바운드)** — MEDRLT 통보서 수신용. **아웃바운드 생성 없음** |
| `claims` 청구 회계 | 제출/심사/지급대사 **회계·변동대가·삭감룰(pre_review)** 완비 — 단, 실 EDI 청구파일 생성은 미구현 |
| `ClaimBatch/ClaimStatement/ClaimSubmission` | 청구 단위 모델 존재(진료과별 명세) |

## 두 작업 스트림

### 스트림 A — 실 수가코드표 (코드 대부분 완료·데이터/키 필요)
- **핵심**: `job_fee_sync`가 이미 data.go.kr 어댑터 완성. **`FEE_API_SERVICE_KEY` 발급·주입**하면 야간 동기화가
  dev seed를 실 수가로 대체.
- **필요(운영자/사용자)**: data.go.kr 보건의료빅데이터 **serviceKey** 발급 + 대상 API(행위/약제/재료 단가)
  엔드포인트 확정. 주입 후 `job_fee_sync` 활성.
- **ERP 작업**: 어댑터 응답 매핑 검증(실 필드 ↔ FeeMaster) — 실 응답 샘플 확보 후 소량.

### 스트림 B — EDI 청구파일 생성 (신규·스펙 선행)
심평원 **전산매체 청구 명세서 EDI**(EDIFACT) 아웃바운드 생성. 구성:
1. **청구파일 포맷**: 심평원 EDI 명세(공고 별표) — 세그먼트 구조(요양기관·수진자·명세서·진료내역·상병).
   `edifact.py`에 **직렬화기(serialize)** 추가(현재 parse만).
2. **수가 산정**: FeeMaster unit_price × 수량 × 가산율(종별/시간/연령) → 청구금액·본인부담·공단부담.
3. **비급여**: benefit_type='비급여'는 청구 제외(환자 전액)·별도 집계.
4. **묶음(bundling)**: 심평원 급여기준 묶음룰(패키지 수가에 포함된 세부/재료 별도청구 금지) — `BundlingRule`
   모델은 이미 있음(삭감 적발용). 청구 생성 시 **선제 적용**(사전심사 pre_review와 공유).

## 단계 계획 (스트림 B)

| Phase | 내용 | 선행 | 상태 |
|---|---|---|---|
| **B0 스펙 확보** | 심평원 EDI 청구 명세 포맷 스펙 + 시험청구 대상(요양기호) + 반려/접수 응답 스펙 | **사용자/심평원 제공 필요** | ⛔ 병목 |
| B1 산정 엔진 | FeeMaster 기반 수가 산정(가산율·본인부담률·비급여 분리)·묶음룰 선적용·실 진료내역(BillingLine) 배선 | FeeMaster(A) | ✅ v1.167~1.169 `claims/claim_calc.py`(적대검토·`calc_for_chart`) |
| B2 EDI 매핑(격리 시드) | 산정 결과→EDI 유사 구조 **버전드 매핑 엔진**(실 포맷 아님·제출 미연결) | — | ✅ v1.167 `claims/edi_mapping.py` (SEED_v0) |
| B2' EDI 직렬화(실) | `edifact.py`에 serialize + 실 세그먼트 매퍼(수진자·명세서·진료내역) — SEED_v0 교체 | **B0 스펙** | ⛔ B0 대기 |
| B3 청구 배치·검증 | ClaimBatch→EDI 파일 생성·자체 검증(차대·필수필드)·미리보기 | B1·B2' | ⛔ B0 대기 |
| B4 제출·접수대사 | 심평원 시험청구 제출·접수/반려 응답 파싱(edifact 파서 재사용)·상태 연계 | B0 시험베드 | ⛔ B0 대기 |

> **v1.167 선구축 완료**: B1 산정 엔진(as-of·종별가산·묶음·본인부담 분리·계산식 노출) + B2 격리 EDI 매핑
> 시드(버전 레지스트리·`_production_ready=False`·제출 미연결). 미리보기 `POST /claims/calc/preview`.
> 실 EDI 직렬화(B2')·배치(B3)·제출(B4)은 **B0 실 포맷 스펙 확보 후** 착수(추측 포맷=반려). 설계 원칙:
> 산정↔매핑 분리 → 포맷 교체 시 매핑만 교체·산정 무변경. 과거 명세는 청구 당시 매핑 버전으로 재생성.

## ⚠ 필요 입력 (지금 없어서 막힘)

1. **심평원 EDI 청구 명세 포맷 스펙**(B0) — 아웃바운드 세그먼트 구조. **이게 없으면 B2/B3 착수 불가**
   (추측 구현=반려). 공고 별표/개발가이드 문서 필요.
2. **data.go.kr serviceKey**(A) — 실 수가코드표 동기화 활성.
3. **시험청구 요양기호·시험베드 접근**(B4) — 실제 제출·검증.
4. **묶음/산정 급여기준 범위**(B1) — 어디까지 자동 적용할지(전체 급여기준은 방대·핵심 룰부터).

## 지금 착수 가능한 것 (스펙 없이)

- **B1 산정 엔진 스켈레톤**: FeeMaster 기반 명세서 금액 산정(가산율·본인부담·비급여 분리)의 **계산 코어**
  — EDI 포맷과 독립. 실 데이터(A) 있으면 검증 가능. **스펙 불요**.
- 스트림 A는 운영자가 serviceKey만 주면 즉시(코드 완료).

## 권고

**B0(포맷 스펙)이 병목.** 스펙 확보 전엔 산정 엔진(B1)까지만 안전하게 선구축하고, EDI 직렬화(B2~)는 실
스펙 확보 후 착수(추측 포맷 금지). 스트림 A(수가 실데이터)는 serviceKey 발급으로 병행.
