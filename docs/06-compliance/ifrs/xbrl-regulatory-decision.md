# G10 — XBRL/전자공시 규제 결정 브리프

> 목적: XBRL 생성기 구축 여부를 **외부 회계사·규제 확인**으로 결정하기 위한 프레이밍.
> ⚠ 이 결정 전에는 XBRL 생성기를 구축하지 않는다(불필요한 것을 만들지 않는다·투기 금지).
> 근거: `ledger-architecture-controls.md` G10. 작성 2026-07-15.

---

## 1. 결정해야 할 질문 (외부 회계사)

**본 의료법인이 재무제표를 XBRL/iXBRL 형식으로 전자공시(예: 금융감독원 DART)할 법적 의무가 있는가?**

- 국내 XBRL 전자공시는 주로 **상장사·외부감사 대상 주식회사**의 DART 제출에 적용.
- **비영리 의료법인**은 통상 **의료기관 회계기준**에 따른 보고 대상이며, DART XBRL 전자공시 의무 대상이 아닐 수 있음.
- 확인 필요: ① 법인 형태·규모(외감 대상 여부) ② 감독기관이 요구하는 제출 형식(XBRL vs PDF/서식) ③ K-IFRS vs 의료기관 회계기준 중 1차 준거.

## 2. 시나리오별 대응

| 확인 결과 | 대응 |
|---|---|
| **XBRL 제출 의무 없음**(가장 가능성 높음) | G10 스코프 **제외**. 현행 재무제표(JSON·xlsx)로 충분. 본 트랙 종결. |
| **XBRL 제출 의무 있음** | 아래 §3 프로젝트 착수(G8 기반). |
| **불확실/장래 대비** | G8 element 태그(§3-2)만 선제 도입, 생성기는 보류. |

## 3. 의무 시 구축 범위 (별도 프로젝트)

1. **택소노미 선정** — K-IFRS DART 택소노미 버전 확정(감독기관 지정).
2. **계정 ↔ IFRS element 매핑** — **G8 기반**. 현재 `accounts.is_current`·`cf_activity`(BS/CF 분류)는 확보. XBRL은 추가로 계정별 **표준 element 태그**(예: `ifrs-full:CashAndCashEquivalents`) 필요 → `accounts.ifrs_element`(String) 컬럼 신설 + 매핑. 커버리지 감사(`/finance/accounts/classification-coverage` 패턴 확장)로 완결도 관리.
3. **인스턴스 생성기** — 재무제표(현 statements.py 산출)를 element 태그로 감싸 XBRL/iXBRL 인스턴스 생성. Arelle 등으로 스키마·계산 검증.
4. **제출 워크플로** — 생성→검증→서명→제출 이력.

**의존**: 2가 G8(계정 element)의 확장. 1·3·4는 규제 확인 후에만 의미.

## 4. 현재 상태 (준비도)

- ✅ G8 데이터 주도 분류(is_current/cf_activity)·커버리지 감사(v1.110~1.111) — XBRL element 매핑의 **선행 기반** 확보.
- ✅ 재무제표 산출(statements.py 4종+비율+부문) — 인스턴스 생성 입력 준비됨.
- ❌ 표준 element 태그(`ifrs_element`)·생성기·제출 워크플로 — **규제 확인 후** 착수.

## 5. 권고

**외부 회계사에게 §1 질문을 확인**하라. 대부분의 비영리 의료법인은 XBRL 전자공시 대상이 아니므로 **G10은 스코프 제외**가 유력하며, 그 경우 본 원장 아키텍처·통제 트랙은 핵심 통제(무결성·추적·마감·분류·다차원·materiality)를 모두 확보한 상태로 **완결**된다. 의무가 확인되면 §3을 별도 프로젝트로 스코핑한다.
