# 하이브리드 아키텍처 검증 명세 — Data-Local / Service-Cloud

> **문서 목적**: CLI 코딩 에이전트(Claude Code 등)가 코드베이스를 이 아키텍처 규칙에
> 대조해 **자동 감사**하기 위한 기계 검증용 명세.
> CLAUDE.md / AGENTS.md에 포함하거나 CI 검증 게이트에서 참조한다.
>
> **적용 패턴**: 컨트롤 플레인(클라우드) / 데이터 플레인(온프렘) 분리형 의료 SaaS.
> **핵심 규칙 한 줄**: *클라우드는 코드와 조율(coordination)을 제공하고, 내용(PHI content)은 절대 만지지 않는다.*

---

## 0. 사용법 (CLI 에이전트용)

이 문서는 두 가지로 쓴다.

1. **정적 감사**: 아래 §7의 "감사 프롬프트"를 Claude Code에 붙여넣어 코드베이스 전체를 스캔.
2. **CI 게이트**: 각 불변식의 `Detection`을 grep/AST 규칙으로 옮겨 PR 차단 조건으로 사용.

**판정 규칙**
- `BLOCKER` 위반이 1건이라도 있으면 → **FAIL** (머지·배포 금지).
- `WARN` 위반은 리포트하되 사람 검토로 판정.
- ⚠️ `사람 결정` 항목은 에이전트가 판정하지 말고 **질문으로 승격**시킨다.

**용어**
- **PHI**: 원본 환자정보 + 파생 정보(추론 출력, 쿼리 결과, 식별자 포함 로그). *파생 PHI도 PHI다.*
- **Cloud tier**: 클라우드에 배포되는 코드 (control plane).
- **On-prem tier**: 병원 내부망에서 실행되는 코드 (data plane).

## 2. PHI 격리 불변식

### INV-PHI-01 — PHI는 클라우드에서 처리되지 않는다
**Assertion**: cloud tier의 어떤 핸들러·서비스도 PHI를 수신·저장·처리·렌더링하지 않는다. cloud tier가 수용하는 입력은 비PHI(테넌트 ID, 인증 토큰, 작업 메타데이터, 비식별 지표)뿐이다.

**Detection (안티패턴)**
- cloud 배포 경로의 코드가 EMR/환자 스토어 DB 커넥션을 연다.
- cloud 핸들러 시그니처/DTO에 환자 식별자, 진단 텍스트, 추론 출력 필드가 있다.
- cloud 서비스가 온프렘 추론/EMR API를 **프록시**하며 응답 바디를 역직렬화한다.
- 환경변수: cloud 배포에 PHI DB URL / 추론 엔드포인트 시크릿이 주입된다.

**Verify**
1. cloud 배포 대상 디렉터리/서비스를 식별한다 (deploy manifest, Dockerfile target, infra as code).
2. 그 경계 안에서 PHI 타입/스키마가 import·참조되는지 데이터 흐름을 추적한다.
3. cloud→client 응답에 PHI 필드가 실리는 경로가 있는지 확인한다.

**Pass**: cloud tier 코드에서 PHI 스키마 참조 0건.

---

### INV-PHI-02 — 클라이언트사이드 렌더링 + 로컬 BFF만
**Assertion**: 환자 데이터는 클라이언트(의사 브라우저/앱)가 **온프렘 로컬 API**에서 직접 fetch해 렌더링한다. 클라우드에서의 PHI 서버사이드 렌더링(SSR)은 금지.

**Detection (안티패턴)**
- Next.js `getServerSideProps` / React Server Component / SSR 경로가 PHI를 fetch한다.
- 서버 렌더된 환자 뷰가 cloud origin에서 서빙된다.
- 클라이언트의 PHI fetch base URL이 cloud origin으로 하드코딩/설정된다 (온프렘 로컬 API가 아니라).

**Verify**
1. PHI를 렌더하는 컴포넌트가 CSR 경계 안에 있는지 확인.
2. PHI API 호출의 base URL이 **온프렘 로컬 엔드포인트**로 해석되는지 설정을 추적.
3. SSR/edge 함수가 PHI를 만지지 않음을 확인.

**Pass**: PHI를 다루는 서버 렌더 경로 0건 + PHI fetch가 로컬 API base로만.

⚠️ **사람 결정**: 프레임워크상 하이드레이션 경계가 모호하면 판정 보류 → 질문 승격.

---

### INV-PHI-03 — 추론 입출력의 온프렘 고정
**Assertion**: SaMD 프로덕션 추론(MedGemma 등)은 온프렘 CUDA에서만 실행되며, 추론 요청/응답 바디(임상 콘텐츠)는 경계를 벗어나지 않는다.

**Detection (안티패턴)**
- 추론 클라이언트가 클라우드 추론 엔드포인트를 호출한다.
- 임상 텍스트/오디오가 cloud 큐·스토리지를 경유한다.
- 추론 출력(차트 초안 = 파생 PHI)이 cloud 서비스로 반환된다.

**Verify**: 추론 호출 경로의 target host가 온프렘으로만 해석되는지, 입출력 바디가 cloud 계층을 통과하지 않는지 추적.

**Pass**: 추론 I/O가 온프렘 네트워크 경계 내부에서만 흐름.

## 3. 경계(gateway) 불변식

### INV-NET-01 — 상향은 가명/집계만
**Assertion**: 온프렘→클라우드 반출 페이로드는 경계에서 비식별/가명화를 거친 데이터 또는 집계 지표뿐이다. 원본 PHI·오디오·성문은 반출되지 않는다.

**Detection (안티패턴)**
- egress 페이로드 스키마에 원본 EMR 필드/오디오 blob/voiceprint 벡터가 있다.
- 반출 전 de-identification/pseudonymization 단계가 코드 경로에 없다.
- "임시로" 원본을 cloud로 보내는 우회 경로 (debug, backup, sync).

**Verify**: 모든 온프렘→cloud 송신 지점을 열거하고, 각 지점 앞에 비식별 변환이 있는지 확인.

**Pass**: 모든 egress가 de-ID/집계 게이트를 통과. 원본 PHI egress 0건.

⚠️ **사람 결정**: 비식별 기법의 재식별 위험 적정성은 에이전트가 판정하지 않는다 (개인정보보호법 가명처리 적정성 검토 필요).

---

### INV-NET-02 — 모델은 하향, 데이터는 상향 안 함
**Assertion**: 경계를 넘는 것은 **모델 아티팩트(가중치)**의 클라우드→온프렘 하향뿐. 서명/체크섬 검증 게이트를 통과해야 배포된다.

**Detection (안티패턴)**
- 모델 배포 파이프라인에 서명/해시 검증이 없다.
- 데이터가 모델과 함께 상향되는 경로.

**Verify**: 모델 배포 경로에 signature/checksum 게이트 존재 확인.

**Pass**: 하향 모델은 검증됨, 상향 데이터 경로 없음.

---

## 4. 관측성 불변식

### INV-TEL-01 — Telemetry/로그 PHI 스크러빙
**Assertion**: APM·에러 로깅·telemetry가 PHI를 소스에서 스크러빙한다. cloud로 선적되는 어떤 로그·트레이스에도 환자 식별자·요청 바디 PHI·PHI 포함 스택트레이스가 없다.

**Detection (안티패턴)** — *가장 흔한 유출 지점*
- 요청 바디/응답 바디 전체를 로깅한다 (`log.info(req.body)` 류).
- 에러 핸들러가 PHI 포함 payload를 그대로 리포트한다.
- cloud APM/Sentry 류 SDK가 온프렘 PHI 경로에서 무필터로 초기화된다.
- 환자 ID가 URL path/query에 노출되고 access log로 cloud 전송된다.

**Verify**
1. 로깅·에러리포팅 호출 지점을 열거.
2. cloud로 전송되는 로그 파이프라인 앞에 PHI 스크러버가 있는지 확인.
3. PHI 필드 화이트리스트/블랙리스트 필터 존재 여부.

**Pass**: cloud-선적 로그 경로에 PHI 스크러빙 계층 존재, 무필터 바디 로깅 0건.

---

## 5. 가용성·안전 불변식

### INV-AVAIL-01 — 클라우드는 하드 디펜던시가 아니다
**Assertion**: 클라우드 컨트롤 플레인이 중단돼도 온프렘 데이터 플레인은 독립적으로 최소 임상 기능(환자 조회·기록 저장)을 유지한다. *판독/기록 보조 + 의사 최종 책임 철학상, AI·클라우드 장애가 진료 기록을 막아서는 안 된다.*

**Detection (안티패턴)**
- 앱 부팅/렌더가 cloud 도달성에 하드 블로킹된다 (cloud 안 되면 화면 안 뜸).
- 인증이 cloud IdP에만 의존하고 로컬 폴백/캐시 세션이 없다.
- 로컬 기록 저장 경로가 cloud 승인/네트워크를 동기 대기한다.

**Verify**: cloud 의존 지점을 열거하고, 각 지점에 로컬 폴백/degradation 경로가 있는지 확인.

**Pass**: cloud 다운 시나리오에서 조회·기록 경로가 로컬만으로 동작.

⚠️ **사람 결정**: 어느 기능까지 degrade 허용할지(가용성 등급)는 임상·규제 판단. 에이전트는 "폴백 부재"만 플래그.

---

### INV-BIO-01 — 성문(생체정보) 격리·동의
**Assertion**: 화자 성문(voiceprint)은 생체정보=민감정보다. 온프렘에 격리 저장하고, **명시적 동의 게이트를 통과한 뒤에만** 취득하며, 경계를 절대 넘지 않는다.

**Detection (안티패턴)**
- voiceprint 취득 경로 앞에 동의 확인 게이트가 없다.
- voiceprint 벡터/원본 오디오가 egress 페이로드·cloud 스토리지에 있다.
- 생체정보가 일반 telemetry에 섞인다.

**Verify**: voiceprint 수명주기(취득→저장→매칭)를 추적, 동의 게이트·온프렘 격리·비반출 확인.

**Pass**: 동의 선행 + 온프렘 격리 + egress 0건.

---

### INV-AUDIT-01 — 경계·접근 감사 로그
**Assertion**: 모든 경계 통과 전송과 PHI 접근은 불변(append-only) 로그로 기록된다. 모델 버전·입력·출력·수치 패리티 로그를 포함해 IEC 62304 감사 추적으로 활용 가능해야 한다.

**Detection (안티패턴)**: 경계 전송/PHI 접근 지점에 감사 로깅이 누락. 로그가 변경 가능(mutable)한 저장소에만 있음.

**Verify**: 경계·접근 지점 대비 감사 로깅 커버리지 확인.

**Pass**: 경계 전송·PHI 접근 100% 로깅 (불변 저장).

## 6. 멀티테넌시 불변식 (weve 배포 매핑)

### INV-TENANT-01 — 컨트롤 플레인은 테넌트 PHI를 안 가진다
**Assertion**: 클라우드 컨트롤 플레인은 테넌트별로 앱·인증·업데이트를 조율하되, 어떤 병원의 PHI도 보유하지 않는다. 각 병원 데이터 플레인은 온프렘 격리된다.

**매핑**
- **클라우드 = 공유 컨트롤 플레인**: 테넌트 관리, SSO(SAML/OIDC), 앱·모델 아티팩트 배포, 비식별 집계.
- **병원별 = 로컬 데이터 플레인**: 자기 PHI 온프렘 격리, 로컬 추론, 로컬 렌더.

**Detection (안티패턴)**
- 컨트롤 플레인 DB에 테넌트 PHI 테이블/필드.
- 테넌트 간 데이터가 공유 스토리지에서 교차 접근 가능.

**Verify**: 컨트롤 플레인 스토리지 스키마에 PHI 부재, 테넌트 격리 경계 확인.

**Pass**: 컨트롤 플레인 PHI 0건 + 테넌트 데이터 플레인 격리.

## 7. CLI 감사 프롬프트 (바로 붙여넣기)

> 아래를 Claude Code / CLI 에이전트에 붙여넣어 코드베이스 정적 감사를 실행한다.

```
이 저장소를 ARCHITECTURE-INVARIANTS.md의 불변식(INV-*)에 대조해 감사하라.

절차:
1. 먼저 cloud tier(control plane)와 on-prem tier(data plane)의 코드 경계를 식별하라.
   - 배포 manifest / Dockerfile target / IaC / 환경설정에서 무엇이 클라우드에
     배포되고 무엇이 온프렘에서 실행되는지 근거와 함께 명시하라.
   - 경계가 코드에서 불명확하면 판정하지 말고 질문으로 승격하라.

2. 각 불변식마다 §Detection의 안티패턴을 코드에서 탐색하고, §Verify 절차를 수행하라.
   PHI에는 파생 PHI(추론 출력, 쿼리 결과, 식별자 포함 로그)를 포함한다.

3. 결과를 다음 형식의 표로 보고하라:
   | INV-ID | 판정(PASS/FAIL/WARN/BOUNDARY-UNCLEAR) | 근거(파일:라인) | 위반 상세 | 수정 제안 |

4. 판정 규칙:
   - BLOCKER 위반 1건 이상 → 전체 FAIL.
   - ⚠️ '사람 결정' 항목은 판정하지 말고 사람에게 물을 질문으로 정리하라.
   - 추측하지 말라. 코드 근거(파일:라인)가 없으면 BOUNDARY-UNCLEAR로 표기하라.

5. 마지막에 다음을 요약하라:
   - BLOCKER 위반 목록 (있으면)
   - 사람 결정이 필요한 질문 목록
   - CI 게이트로 자동화 가능한 항목 vs 수동 검토가 필요한 항목
```

## 9. ⚠️ 사람 결정 지점 (에이전트가 판정하지 않음)

이 항목들은 임상·규제·법적 판단이므로 코드 감사로 결론짓지 않는다.

1. **준거 규제 확정**: 병원이 공공(→N2SF 직접 대상) vs 사립(→의료법·개인정보보호법·EMR 클라우드 규정·CSAP). 이에 따라 클라우드 계층의 인증 요건이 갈림.
2. **CSO 데이터 등급 분류**: 각 데이터/워크로드의 기밀(C)·민감(S)·공개(O) 판정.
3. **비식별 적정성**: 가명처리가 재식별 위험 기준을 충족하는지 (개인정보보호법 적정성 검토).
4. **CSAP 인증 등급**: 민감정보 취급 시 요구되는 클라우드 인증 수준 + 국내 리전 요건.
5. **가용성 등급**: degradation 시 어느 임상 기능까지 허용/차단할지.
6. **MedGemma 라이선스**: 상용 SaMD 배포 전 Health AI Developer Foundations 라이선스 법률 검토.
